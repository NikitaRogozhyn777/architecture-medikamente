1.  **Выявление конфиденциальных данных и построение Data Flow Diagrams (DFD)**

    ### Анализ информации и выявление конфиденциальных данных:

    На основе описания можно выделить следующие категории конфиденциальных данных, требующих защиты в соответствии с 152-ФЗ "О персональных данных":

    *   **Персональные данные (PII):**
        *   ФИО
        *   Дата рождения
        *   Контактные данные (телефон, email)
        *   Адрес прописки
        *   Место работы/учёбы
        *   Данные паспорта (вероятно, используются для договоров)

    *   **Специальные категории персональных данных (СПДн):**
        *   Данные о здоровье (диагнозы, заключения врачей, история болезней)
        *   Результаты медицинских анализов
        *   Информация о хронических заболеваниях

    *   **Финансовые данные:**
        *   Реквизиты договоров
        *   История платежей (интегрирована с PII)

    *   **Данные ТМЦ (менее критично, но тоже важно):**
        *   Информация о закупках оборудования и медикаментов.

    **Проблема:** Большая часть этих данных (PII, СПДн) хранится в неконтролируемых файлах (Excel, JPG, PDF) на общем сетевом диске без разграничения доступа и аудита.

2.  **Аудит мер безопасности и проблемные зоны**

    ### Сопоставление с требованиями и лучшими практиками:

    | Принцип / Требование (152-ФЗ, Privacy by Design) | Текущее состояние (As-Is) | Проблемная зона / Рекомендация |
    | :--- | :--- | :--- |
    | **Конфиденциальность** | Данные хранятся в открытом виде на общем диске. Нет шифрования ни на rest, ни на transit. | Высокий риск утечки. Необходимо внедрить шифрование дисков, шифрование каналов передачи данных (TLS) и шифрование на уровне БД для чувствительных полей. |
    | **Целостность** | Данные могут быть изменены любым пользователем с доступом к папке. Нет механизмов контроля версий или журналирования изменений для файлов Excel. | Рекомендация: Переход на СУБД с соблюдением ACID-требований, ведение логов изменений критичных данных. |
    | **Доступность** | Сервер расположен в том же здании. Нет информации о RAID, резервном копировании и планах восстановления. | Риск потери данных и простоя. Необходимо реализовать отказоустойчивую инфраструктуру, регулярное бэкапирование и его тестирование. |
    | **Законность обработки (согласие)** | Скорее всего, согласие на обработку ПДн собирается на бумаге и хранится в сканах. Нет системы управления согласиями, напоминаний об истечении срока действия. | Риск нарушения 152-ФЗ. Необходима интеграция электронного сбора и учёта согласий в новую CRM/портал. |
    | **Minimization (Минимизация данных)** | Собираются расширенные данные (адрес, место работы). Нет политики очистки данных: старые и неактуальные данные хранятся вечно. | Риск: Хранение избыточных данных увеличивает площадь атаки и сложность управления. Нужно определить политики хранения и архивации. |
    | **Purpose Limitation (Ограничение цели)** | Данные, собранные для мед. целей, используются бухгалтерией для платежей и налоговой отчётности без чёткого разграничения. | Риск: Использование данных не по целям сбора. Необходимо чётко разделять домены данных и настраивать доступ в соответствии с необходимостью. |
    | **Accountability (Подотчётность)** | Полностью отсутствует аудит действий пользователей. Невозможно узнать, кто, когда и какие данные пациента просматривал или изменял. | Критическое нарушение. Необходимо внедрить систему логирования и аудита всех действий с конфиденциальными данными. |
    | **Security by Design** | Системы разрабатывались и внедрялись без учёта безопасности на архитектурном уровне. Безопасность не является неотъемлемой частью процессов разработки. | Рекомендация: Внедрить практики DevSecOps, статический и динамический анализ кода, проверки зависимостей на этапах CI/CD. |
    | **Data Lineage** | Отследить происхождение данных и их движение между системами (Excel -> 1C -> Excel) практически невозможно. | Рекомендация: Использовать инструменты управления метаданными и Data Lineage (напр., OpenLineage) в новом Data Lake для отслеживания происхождения данных. |

    ### Сводный список проблемных зон:

    *   **Небезопасное хранение данных:** Критичные PII и СПДн в открытых файлах на общем диске.
    *   **Отсутствие контроля доступа:** Нет RBAC/ABAC, любой сотрудник может получить доступ ко всем данным.
    *   **Отсутствие аудита:** Невозможно отследить действия пользователей с данными.
    *   **Небезопасные каналы передачи:** Данные передаются между системами и отделами без шифрования.
    *   **Неуправляемые согласия:** Нет системы для сбора и учёта согласий на обработку ПДн.
    *   **Смешение данных:** Бухгалтерские, медицинские и складские данные слабо разделены, что ведёт к избыточному доступу.
    *   **"Замок из песка":** Периметр безопасности (домен) есть, но внутри периметра контроля нет.
    *   **Ручная обработка:** Высокий риск человеческой ошибки, ведущей к утечке или потере данных.


3.  **Предложения по улучшению**

    ### Список данных для защиты и способы защиты:

    | Категория данных | Данные | Способ защиты (в rest) | Способ защиты (in transit) | Дополнительные меры |
    | :--- | :--- | :--- | :--- | :--- |
    | **PII** | ФИО, телефон, email, адрес | Шифрование (симметричное, AES-256) | TLS 1.3 | Обезличивание (для аналитики в BI) |
    | **СПДн** | Диагнозы, анализы, заключения | Шифрование (симметричное, AES-256) | TLS 1.3 | Строгий RBAC, маскирование для всех, кроме врача |
    | **Аутентификационные данные** | Пароли, хэши | Хэширование (с солью, алгоритмом bcrypt) | TLS 1.3 | MFA для доступа ко всем системам |
    | **Финансовые данные** | Реквизиты договоров, суммы | Шифрование | TLS 1.3 | Обфускация (замена на токены в логах) |
    | **Данные ТМЦ** | Названия, кол-во, цены | (Менее критично) | TLS 1.3 | — |

    ### Механизм тегирования данных:

    Необходимо внедрить систему классификации и тегирования данных на основе меток (labels/tags).

    **Формат тегов:** `confidentiality_level::data_category::purpose`

    **Примеры тегов:**
    *   `pii::personal::registration` (ФИО, телефон для регистрации)
    *   `spdn::health::diagnosis` (Диагноз, результаты анализов)
    *   `financial::contract::billing` (Реквизиты договора)

    **Инструменты тегирования:**
    *   **На уровне приложения:** Логика в коде backend-сервисов (Java/Spring) автоматически проставляет теги к данным при их создании/изменении.
    *   **На уровне БД:** Использование возможностей СУБД (например, в PostgreSQL можно использовать комментарии к столбцам или отдельные таблицы-справочники для метаданных).
    *   **На уровне Data Lake:** Использование инструментов вроде Apache Atlas или OpenMetadata для автоматического сканирования и тегирования данных на основе политик.

    **Использование тегов:**
    *   **Контроль доступа:** Система авторизации (например, на основе OPA - Open Policy Agent) проверяет не только роль пользователя, но и теги запрашиваемых данных.
    *   **Мониторинг и аудит:** SIEM-система (например, на базе Elasticsearch) может анализировать логи и генерировать алерты при попытке доступа к данным с тегом `spdn` неавторизованным пользователем.
    *   **Проверка в CI/CD:** Статический анализ кода (SAST) может проверять, что код, работающий с данными, помеченными как `spdn`, не логирует их в открытом виде.

    ### Список инструментов и мер для обеспечения конфиденциальности:

    **Infrastructure:**
    *   **Шифрование дисков:** BitLocker (для Windows) или LUKS (для Linux-серверов).
    *   **Сети и передача данных:** VPN для удалённого доступа, TLS 1.3 для всего внутреннего и внешнего трафика (service mesh типа Linkerd или Istio).
    *   **Secrets Management:** HashiCorp Vault или Kubernetes Secrets (вкупе с внешним софтом, например, Sealed Secrets) для хранения ключей шифрования, паролей, токенов.

    **Data & Application:**
    *   **База данных:** PostgreSQL (уже в стеке техдира) с расширением `pgcrypto` для шифрования на уровне БД. Разделение данных по схемам/базам.
    *   **Управление доступом:** RBAC на основе ролей в AD/LDAP + ABAC для сложных сценариев (использование OPA).
    *   **Аудит:** Включение детального логирования в PostgreSQL + отправка логов в Elasticsearch (уже в стеке) для анализа и алертинга.
    *   **Маскирование/Обезличивание:** Инструменты для генерации тестовых данных или маскирования реальных данных для сред разработки/аналитики (например, Apache Griffin).

    **Processes:**
    *   **DevSecOps:** Интеграция сканеров SAST/DAST (например, SonarQube, OWASP ZAP) в pipeline CI/CD (в Jenkins/GitLab CI).
    *   **Управление уязвимостями:** Регулярное сканирование образов Docker и зависимостей (Trivy, Snyk).
    *   **Согласия:** Разработать модуль в новой CRM для электронного сбора, хранения и управления согласиями с напоминаниями об истечении срока.
