# План миграции на новую архитектуру

## 1. Анализ ситуации

### Текущее состояние (As-Is)
Монолитная, небезопасная система на базе разрозненных продуктов (1С, Excel, файловый сервер). Данные хранятся хаотично, процессы ручные. Система не готова к масштабированию.

### Целевое состояние (To-Be)
Микросервисная, безопасная, отказоустойчивая архитектура, соответствующая требованиям 152-ФЗ. Автоматизированные процессы, единая точка входа (API Gateway), разделённые базы данных.

### Ключевые компоненты, затрагиваемые миграцией:

- **Базы данных**: Перенос данных из Excel, сканов и 1С в реляционную БД (PostgreSQL) и Data Lake (ClickHouse + MinIO)
- **Бизнес-логика**: Выделение и декомпозиция бизнес-процессов (запись, приём, оплата, учёт ТМЦ) в отдельные микросервисы
- **Коммуникационные каналы**: Замена неструктурированного обмена файлами на API с четкими контрактами и шифрованием (TLS/mTLS)
- **Серверное оборудование**: Переход с физического сервера Windows на отказоустойчивый Kubernetes-кластер
- **Пользовательские интерфейсы**: Разработка новых порталов (клиент, сотрудник) взамен ручных процессов в Excel

## 4. Краткий список приоритетных мер

- **Критический приоритет**: Нанять ключевых специалистов (DevOps, архитектор) и привлечь юриста по ИБ для проверки соответствия 152-ФЗ.

- **Высокий приоритет**: Начать аудит и очистку данных. Развернуть managed Kubernetes-кластер и настроить базовый CI/CD.

- **Высокий приоритет**: Разработать поэтапный план миграции (roadmap) с четкими MVP (например, сначала только запись через портал, потом интеграция с 1С, потом перенос данных).

- **Средний приоритет**: Начать обучение сотрудников и коммуникацию о предстоящих изменениях.

**Вывод**: Основные риски миграции носят не технический, а организационный и кадровый характер. Успех зависит от правильного управления проектом, привлечения компетенций и активной работы с данными. Технические риски нивелируются выбором managed-решений и постепенным, а не "Big Bang", подходом к внедрению.
