# Политика классификации и защиты данных

## 1. Классификация данных для защиты

Данные классифицируем по типу, чувствительности и профилю риска в соответствии с законодательством РФ (152-ФЗ) и лучшими практиками.

| Категория данных | Примеры | Чувствительность | Профиль риска | Состояние данных |
| :--- | :--- | :--- | :--- | :--- |
| **СПДн (Спец. категории ПДн)** | Диагнозы, истории болезней, результаты анализов, заключения врачей, назначения | Критически высокая | Очень высокий. Утечка ведет к огромным репутационным потерям, судебным искам и штрафам по 152-ФЗ. | At Rest, In Transit, In Use |
| **PII (Персональные данные)** | ФИО, паспортные данные, дата рождения, телефон, email, адрес прописки, фото | Высокая | Высокий. Утечка ведет к нарушению 152-ФЗ, фишингу, мошенничеству и потере доверия клиентов. | At Rest, In Transit |
| **Аутентификационные данные** | Хэши паролей, токены доступа, сессии, сертификаты | Высокая | Высокий. Компрометация ведет к несанкционированному доступу ко всей системе. | At Rest, In Transit |
| **Финансовые данные** | Реквизиты договоров, суммы платежей, банковские реквизиты компании | Высокая | Высокий. Прямой финансовый ущерб, мошенничество. | At Rest, In Transit |
| **Метаданные операций** | Время записи, ID врача, ID услуги, логи доступа | Средняя | Средний. Может быть использовано для анализа деятельности и деанонимизации других данных. | At Rest, In Transit |
| **Данные ТМЦ** | Названия медикаментов, оборудования, их количество, цены закупки | Низкая/Средняя | Низкий. Коммерческая тайна. Прямого ущерба клиентам нет. | At Rest |

## 2. Реализация базовых инструментов защиты

Для каждой категории данных и состояния применяются свои инструменты.

### Data in Transit (Данные в движении)

**Цель:** Защита от перехвата и подмены данных при передаче по сети.

**Инструмент:** TLS 1.3 (или как минимум TLS 1.2).

**Реализация:**

- **Внешняя связь:** Все взаимодействия с пользовательскими приложениями (портал, мобильное приложение) через API Gateway должны использовать обязательный TLS.
- **Внутренняя связь (Service-to-Service):** Вся коммуникация между микросервисами внутри Kubernetes-кластера должна использовать mTLS (mutual TLS), реализуемый с помощью Service Mesh (например, Istio или Linkerd). Это обеспечивает аутентификацию как сервера, так и клиента.
- **Интеграция с партнерами:** Обмен данными с лабораторией должен использовать mTLS для взаимной аутентификации и шифрования канала.

### Data at Rest (Данные в покое)

**Цель:** Защита данных на носителях от несанкционированного доступа при краже или утере.

**Инструмент 1: Шифрование дисков (Full Disk Encryption - FDE)**
- **Что защищает:** Все данные на физических и виртуальных дисках.
- **Реализация:** LUKS (для виртуальных машин с Linux), BitLocker (для Windows-серверов, например, для 1С). Это защищает от физического изъятия дисков.
- **Уровень:** Инфраструктурный.

**Инструмент 2: Шифрование на уровне БД (Transparent Data Encryption - TDE)**
- **Что защищает:** Файлы данных, временные файлы и бэкапы СУБД.
- **Реализация:** Использование встроенных возможностей СУБД. PostgreSQL (основная БД) поддерживает шифрование через расширения (например, pgcrypto для шифрования отдельных столбцов) или с помощью сторонних инструментов. Для ClickHouse также есть механизмы шифрования.
- **Уровень:** Базы данных.

**Инструмент 3: Шифрование на уровне приложения (Application-Level Encryption)**
- **Что защищает:** Наиболее ценные данные (СПДн, паспортные данные).
- **Реализация:** Критичные данные шифруются самим сервисом (например, Medical Records Service) перед записью в БД с использованием сильных алгоритмов (AES-256-GCM). Ключи хранятся не в БД, а в отдельном Vault. Это дает защиту даже от DBA-администраторов.
- **Уровень:** Наиболее granularный и безопасный.

### Data in Use (Данные в использовании)

**Цель:** Защита данных в оперативной памяти (например, от дампа памяти).

**Проблема:** Самый сложный для защиты аспект. Данные должны быть в расшифрованном виде для обработки.

**Меры:**

- **Аппаратное обеспечение:** Использование технологий типа Intel SGX (Trusted Execution Environments) пока сложно и дорого для старта.
- **Операционные меры:** Минимизация времени нахождения данных в памяти, своевременная очистка (zeroing) буферов в памяти после использования. Жесткий контроль доступа к серверам приложений.

## 3. Автоматизированный контроль

**Цель:** Постоянный мониторинг и принудительное применение политик безопасности.

**Инструмент 1: HashiCorp Vault**
- **Роль:** Централизованное управление секретами (ключи шифрования, сертификаты, токены).
- **Для шифрования:** Vault может выступать в роли Key Management Service (KMS), автоматически вращая ключи шифрования и предоставляя их сервисам по запросу (через API) для шифрования/расшифровки данных. Это реализует автоматизированный контроль над ключами.

**Инструмент 2: Service Mesh (Istio/Linkerd)**
- **Роль:** Автоматическое наложение политик mTLS для всего трафика между сервисами. Политика "по умолчанию запрещено" — любой трафик без mTLS блокируется.

**Инструмент 3: Policy-as-Code с Open Policy Agent (OPA)**
- **Роль:** Автоматическая проверка конфигураций на безопасность.
- **Пример:** В пайплайне CI/CD с помощью OPA можно проверять, что в конфигурационных файлах не зашиты plain-text секреты, или что для сервиса, работающего с СПДн, обязательно настроено шифрование на уровне приложения.

**Инструмент 4: Система мониторинга и алертинга (Prometheus/VictoriaMetrics + Alertmanager + Grafana)**
- **Роль:** Мониторинг работы Vault, истечения срока действия сертификатов TLS, попыток несанкционированного доступа к зашифрованным данным.

## 4. Реестр программных и аппаратных средств для защиты данных

| Данные | В чём необходимость защиты | Инструменты защиты |
| :--- | :--- | :--- |
| **СПДн (в БД)** | Необходима максимальная защита от любого несанкционированного доступа, включая администраторов БД. | Шифрование на уровне приложения (AES-256) + Управление ключами (HashiCorp Vault). Данные шифруются сервисом перед записью в БД. |
| **PII (в БД)** | Защита от утечки в случае компрометации БД или доступа к бэкапам. | Шифрование на уровне БД (TDE, pgcrypto) и/или шифрование на уровне приложения для особо чувствительных полей (паспорт). |
| **PII/СПДн (в передаче)** | Защита от перехвата (сниффинга) при передаче между сервисами и к клиенту. | TLS 1.3 для внешнего трафика, mTLS (Istio/Linkerd) для внутреннего трафика между микросервисами. |
| **Аутентификационные данные** | Защита от кражи паролей и токенов. Нельзя хранить в открытом виде. | Хэширование с солью (алгоритм bcrypt/scrypt) для паролей. HashiCorp Vault для хранения токенов и прочих секретов. |
| **Финансовые данные** | Защита от мошенничества и несанкционированного доступа. | Шифрование на уровне БД (TDE). |
| **Все данные (на дисках)** | Защита от физической кражи серверов/дисков. | Полное шифрование дисков (FDE): LUKS (Linux), BitLocker (Windows). |
| **Резервные копии** | Защита от утечки при хранении или транспортировке бэкапов. | Шифрование бэкапов средствами СУБД (pg_dump с шифрованием) или инструментов бэкапирования (e.g., Borg, Restic). Ключи от бэкапов хранить отдельно от самих бэкапов. |
| **Данные ТМЦ** | Защита коммерческой тайны (цены закупок). | |
