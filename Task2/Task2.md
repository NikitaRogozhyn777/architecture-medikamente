# 1. Новые блоки в архитектуре C4 для соблюдения Privacy by Design

Текущая архитектура (As-Is) монолитна, небезопасна и не масшташируема. Целевая архитектура (To-Be) должна быть микросервисной, с чётким разделением ответственности и встроенными механизмами безопасности.

## Ключевые принципы Privacy by Design

- **Proactive not Reactive; Preventative not Remedial**: Предотвращаем угрозы до их появления, а не боремся с последствиями
- **Privacy as the Default Setting**: Система по умолчанию защищает данные пользователя без необходимости каких-либо действий с его стороны
- **Privacy Embedded into Design**: Приватность встроена в архитектуру и дизайн систем, а не добавлена позже
- **Full Functionality — Positive-Sum, not Zero-Sum**: Мы не жертвуем функциональностью ради безопасности, а находим решения, обеспечивающие и то, и другое
- **End-to-End Security — Full Lifecycle Protection**: Данные защищены на всём пути их жизненного цикла — от создания до удаления
- **Visibility and Transparency — Keep it Open**: Все процессы обработки данных прозрачны и поддаются аудиту
- **Respect for User Privacy — Keep it User-Centric**: Пользователь сохраняет контроль над своими данными

## Предлагаемые новые блоки и компоненты в модели C4

На уровне Container Diagram предлагается следующая целевая архитектура:

![Container diagram (To Be)](./diagrams/architecture-medikamente-Container%20diagram%20(To%20Be).drawio.png)

### 1. API Gateway (Kong / Apache APISIX / Spring Cloud Gateway)
**Роль**: Единая точка входа для всех внешних и внутренних запросов
**Реализация PbD**: Встроенные политики аутентификации, авторизации (интеграция с OPA), rate limiting, проверка данных (валидация контрактов), сквозное шифрование (TLS termination)

### 2. Сервис аутентификации и авторизации (на базе Keycloak / Hydra)
**Роль**: Centralized Identity & Access Management (IAM)
**Реализация PbD**: Поддержка стандартов OAuth 2.1 / OpenID Connect, MFA, управление ролями (RBAC) и атрибутами (ABAC)

### 3. Сервисы предметной области (Microservices)
- **Patients Service**: Управление PII и согласиями. Минимизация данных
- **Appointments Service**: Управление записями
- **Medical Records Service**: Управление СПДн. Шифрование данных перед сохранением
- **Billing Service**: Управление платежами
- **Inventory Service**: Управление ТМЦ

**Реализация PbD**: Каждый сервис отвечает за свою зону данных. Разделение ответственности

### 4. Сервис аудита и логирования (Elasticsearch + Logstash + Kibana)
**Роль**: Централизованный сбор логов всех действий пользователей и систем
**Реализация PbD**: Видимость и прозрачность. Неизменяемые логи для расследования инцидентов

### 5. Сервис управления согласиями (Consent Management Service)
**Роль**: Сбор, хранение, управление жизненным циклом согласий пациентов
**Реализация PbD**: User-Centric подход. Автоматическое удаление данных при отзыве согласия

### 6. Сервис обезличивания/маскирования данных (Data Anonymizer Service)
**Роль**: Преобразование чувствительных данных в пригодные для аналитики и тестирования
**Реализация PbD**: Минимизация и безопасность по умолчанию

### 7. Хранилища данных
- **Operational Data Store (PostgreSQL)**: Основная БД для транзакционных данных
- **Data Lake / Warehouse (ClickHouse + MinIO/S3)**: Для аналитики и ML

### 8. Open Policy Agent (OPA)
**Роль**: Движок для принятия решений об авторизации на основе политик
**Реализация PbD**: Гибкая и прозрачная авторизация (ABAC)

# 2. Аналитический слой с учётом принципов Privacy by Design

Аналитический слой должен позволять извлекать ценную информацию из данных, не нарушая приватность пациентов.

## Целевая архитектура аналитического слоя

**Источник данных**: Только обезличенные и агрегированные данные из Data Lake

## Процесс подготовки данных (Data Pipeline)

**Инструменты**: Apache Airflow / Dagster / Prefect

**Процесс**:
1. **Извлечение**: Данные из операционных сервисов попадают в "сырую" зону Data Lake
2. **Трансформация и обезличивание**: Data Anonymizer Service применяет методы:
   - Псевдонимизация
   - Генерализация
   - Сокрытие (Masking)
   - Агрегация
3. **Загрузка**: Обезличенные данные помещаются в "чистую" зону Data Lake

## BI и ML инструменты

- **BI-системы** (Superset, Metabase, Tableau): Подключаются к обезличенным данным
- **ML/AI платформы** (JupyterHub, Kubeflow): Исследователи работают только с обезличенными датасетами

## Data Catalog и Governance (Apache Atlas / OpenMetadata)

**Роль**: Каталог данных, автоматически сканирует источники и тегирует чувствительные данные
**Реализация PbD**: Обеспечивает видимость и прозрачность. Отслеживание lineage данных
